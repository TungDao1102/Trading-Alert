## G-2003
- Outcome: DOWNGRADED. Severity now LOW (placement disabled, nothing observed on a host). Mainnet with placement on: MEDIUM, down from HIGH.
- Independent evidence
  - `snapshot/src/live/config.py:395-427` `live_liveness_problem`: returns None (live) when there is no held marker and the stamp is readable, not in the future and not older than `bound_ms`. It never reads `stamp.mode` or `stamp.tasks`.
  - `snapshot/src/live/runtime.py:270-286` `_liveness` (the probe the heartbeat runs): only calls `live_liveness_problem`. `runtime.py:289-333` `_healthcheck` (the docker probe) prints `tasks`, but `healthy` comes only from `live_liveness_problem`; it is a local probe anyway.
  - `snapshot/src/live/wiring.py:1101-1102, 1160-1168`: the liveness task writes the stamp on its own cadence whatever the other tasks did; `tasks` maps scheduler task results to PASS/FAIL (exceptions), not health-check statuses. `health_tick_once` (`src/live/health.py:487-524`) returns a RED verdict normally, so the health task itself is PASS even when `telegram_delivery` or `unprotected_positions` FAIL; the RED verdict is only journaled to the DB and logged (`log.warning("live.health.not_ok")`).
  - `snapshot/deploy/heartbeat.sh:347-372` `run_once` for `--target live`: success ping only if `python -m src.live.runtime --liveness` exits 0; `send_ping` (line ~318) sends only the URL to curl, no body or status payload. With `--fail-ping`, a fail ping only on probe failure.
  - Probe (`tmp/verify_V4_alerting/probe.py`, snapshot on PYTHONPATH): stamp written 5 s old with `tasks = {protection, alert_drain, health, reconcile: FAIL}` gave `live_liveness_problem(...) -> None` (counted as live).
  - RUNBOOK 11.9 (`docs/operations/RUNBOOK.md:281`) says the signal "does not show that positions are protected"; 22.5 (line 1180) and D106 describe the live check as a probe of `--liveness`. D042 condition 1 only asks that the monitor alert "when any long-running process stops". No other off-host channel (mail, second chat, log shipping, Binance-side alert) is documented or built; `/status` needs Telegram itself.
- Counter-checks performed (attempts to refute)
  - Heartbeat contents: binary, no payload. Refutation fails.
  - Health endpoints: `--healthcheck` is local docker health with the same verdict; no published port (D106). Refutation fails.
  - Process exit on critical state: no `sys.exit`/loop stop on SAFE_MODE, EMERGENCY_CLOSE_FAILED or Telegram failure in `src/live`; only a hung event loop (stale stamp) or a held start reaches the monitor. Refutation fails.
  - Mitigations that lower severity (why DOWNGRADED): `telegram_delivery` and `unprotected_positions` are among the ten checks of the verdict (`src/ops/health.py:63-72`), and a RED verdict is NO_TRADE (`src/live/enablement.py:274`, `src/live/signal_source.py:560,584`), so a Telegram outage or a naked position blocks new entries. Approvals themselves go through Telegram, so no new trade can open without it. A position without a stop is closed by `src/execution/emergency_close.py` (failure leads to SAFE_MODE `EMERGENCY_CLOSE_FAILED` plus a CRITICAL alert, lines 920-955). The residual risk is an open position whose stop placement AND emergency close both fail while the single CRITICAL Telegram alert is not delivered; per `src/live/alerts.py` header (WR-C6) a failed CRITICAL send is not re-queued until restart. Telegram-only is also the only path for SAFE_MODE notice, which by itself is fail-safe (no entries), not a loss.
- Notes: The claim is accurate as stated (DESIGN gap, single human channel). Judged against accepted practice for an unattended system that holds leveraged positions, an independent out-of-band alert for "critical state" is expected; the cheap fix is to make `--liveness` (or a second check) fail on SAFE_MODE, on a RED `unprotected_positions`/`telegram_delivery` verdict or on an undelivered CRITICAL alert, so the existing healthchecks.io check also covers them. Layered automatic fail-closed responses justify MEDIUM rather than HIGH for mainnet.
