## Warnings

### WR-01: `assemble()` docstring omits the two new failure modes

**File:** `src/backtest/experiment.py:192-196`
**Issue:** The `Raises:` block still documents only
`UnregisteredParameterSet` and `IncompleteExperimentRecord`. Since 07.1-01,
`assemble()` can also raise `CostModelBindingMismatch` (present-but-unequal
cost slice, via `src/backtest/binding.py:56-61`) and bare `KeyError`
(registry set predates the 7-key vocabulary — the slice comprehension at
`src/backtest/binding.py:54` raises before `build_cost_model` runs, e.g.
every `baseline-v2` set). Any caller written against the documented
contract — e.g. catching only the two listed exceptions around a batch
assembly loop — will see an uncovered exception type escape. The new test
module proves both paths exist, so the docstring is now factually stale.
(Re-verified: gate call at line 203 unchanged; docstring lines 192-196
unchanged.)
**Fix:** Extend the `Raises:` block:

```python
Raises:
    UnregisteredParameterSet: parameter_set_id not in registry.
    IncompleteExperimentRecord: any identity field missing or
        malformed.
    CostModelBindingMismatch: caller-supplied cost_model hash differs
        from the registry-derived slice (assembly refusal, D-03).
    KeyError: registry set lacks one of the seven COST_KEYS
        (pre-7-key sets such as baseline-v2; fail closed, never
        translated — D-02/D-05).
```

### WR-02: `build_cost_model` `str()` coercion defeats `CostModel` strict string validation

**File:** `src/backtest/costs.py:147,151-152` (pre-existing lines, newly load-bearing via the gate)
**Issue:** `build_cost_model` coerces the three string-valued cost keys with
`str(...)`, while `CostModel.__post_init__` strictly requires non-empty
`str` (lines 116-119). The coercion runs first, so a mistyped fixture value
such as `funding_treatment: None` or `123` is silently converted to
`"None"`/`"123"` and sails past the strict check that was designed to catch
exactly that. The failure then surfaces downstream as a hash mismatch
(`CostModelBindingMismatch`) rather than at the true fault (wrong type),
misdirecting debugging. The registry side cannot produce non-strings
(`_check_param_types` enforces `STRING_KEYS` at
`src/domain/registry.py:294-299`), so this only masks fixture/caller-side
authoring errors — but fail-closed posture prefers the loud type error at
the boundary. Flagged because 07.1 promotes `build_cost_model` to a
security-relevant comparison primitive on both sides of the gate (expected
model AND caller model both flow through it). (Re-verified: coercion and
strict check both unchanged.)
**Fix:**

```python
def _require_cost_str(value: object, field_name: str) -> str:
    if not isinstance(value, str) or value == "":
        raise TypeError(f"{field_name} must be a non-empty string, got {value!r}")
    return value
```

and use it in place of the three `str(...)` calls in `build_cost_model`.
Note: verify no existing fixture relies on non-str coercion before shipping
(all phase6/phase7.1 fixtures use strings, so this is safe).

### WR-03: `CostModel.__post_init__` validates int fields without normalizing them, so direct construction hashes differently from `build_cost_model` for the same logical value (NEW — deep-only)

**File:** `src/backtest/costs.py:96-103,123`
**Issue:** `__post_init__` calls `_coerce_decimal(getattr(self, fname),
fname)` for the four numeric fields but DISCARDS the result — validation
only, no normalization. The hash at line 123 is then computed from the raw
stored fields. Consequence, proven from `src/domain/canonical.py:48-49,67`:
`Decimal("1")` canonicalizes to the JSON string `"1"`, while a raw `int`
`1` passes through as the JSON number `1` — different bytes, different
`cost_model_hash`. So `CostModel(fee_rate_entry=1, ..., cost_model_hash="")`
and `build_cost_model({"fee_rate_entry": 1, ...})` (which coerces to
`Decimal(1)` at lines 54-55) produce DIFFERENT hashes for the logically
identical model. Two construction paths, two identities. Impact is strictly
fail-closed, never fail-open: a directly-constructed int-carrying model can
only spuriously REFUSE at the gate (its JSON-number hash can never equal a
registry-derived JSON-string hash), never spuriously accept — hence Warning,
not Critical. All in-scope callers currently use `build_cost_model`, so no
live mismatch; but the gate's comparison primitive now has a
construction-path-dependent identity, and a future caller constructing
`CostModel` directly (the dataclass constructor is public) will hit an
inexplicable refusal. Cross-module: standard-depth could not see this
because it requires tracing `__post_init__` → `canonical_scalars` type
dispatch together.
**Fix:** Normalize in `__post_init__` so both paths converge:

```python
for fname in (
    "fee_rate_entry",
    "fee_rate_exit",
    "expected_slippage",
    "partial_fill_fraction",
):
    object.__setattr__(self, fname, _coerce_decimal(getattr(self, fname), fname))
```

placed before the range checks and hash computation. Then direct-int and
builder-int models hash identically (both `Decimal(1)` → `"1"`).

### IN-01: `binding.py` docstring misattributes the `KeyError` source (propagated into a test docstring)

**File:** `src/backtest/binding.py:16-17,52` and `tests/test_backtest_binding.py:237`
**Issue:** Both the module docstring and the function docstring state that
absent slice keys "propagate as bare `KeyError` from `build_cost_model`".
In fact the `KeyError` is raised one line earlier, by the slice
comprehension `{k: parameter_set.params[k] for k in COST_KEYS}` (line 54) —
`build_cost_model` is never reached on that path. The Beh. 6 test docstring
(`test_backtest_binding.py:237`) repeats the same misattribution
("propagates bare KeyError from build_cost_model"), so the error has already
propagated to a second file. Behavior matches the locked D-02 decision
either way; only the attribution is wrong, which could mislead a future
refactor (e.g. someone wrapping the `build_cost_model` call in a try/except
`KeyError` and believing they covered the slice path — they would,
coincidentally, since both statements share the function scope, but for the
wrong reason). (Re-verified: lines 16-17, 52, 54 and test line 237
unchanged.)
**Fix:** Reword to "Absent slice keys raise bare `KeyError` from the
registry-slice lookup (`parameter_set.params[k]`), before `build_cost_model`
runs — fail closed, never silent defaults (D-02)." Apply in all three
places.

### IN-02: Bare `KeyError` carries no set-identity context

**File:** `src/backtest/binding.py:54`
**Issue:** On the missing-slice path the raised `KeyError` contains only the
key name (e.g. `'funding_treatment'`). In a batch-assembly log this does not
identify which `strategy_id/parameter_set_id` was unbindable. The bare-type
lock from D-02/D-05 must be respected — do NOT translate into
`CostModelBindingMismatch` — but the payload can be enriched while keeping
the type. (Re-verified: line 54 unchanged, no try/except on the gate path.)
**Fix (optional, preserving the lock):**

```python
try:
    registry_slice = {k: parameter_set.params[k] for k in COST_KEYS}
except KeyError as exc:
    raise KeyError(
        f"{parameter_set.strategy_id}/{parameter_set.parameter_set_id} "
        f"lacks cost key {exc}"
    ) from exc
```

Type stays `KeyError`; message names the set.
