## Notes for the user (and for the RUNBOOK, already recorded there)

- **Repeated `deploy/update.sh --ref` overwrites `.deploy/last-good.env`:** after a half-failed update, roll back first. (RUNBOOK 14.4)
- **Old `restore-*` and `drill-*` directories** stay in the `backupdata` volume and need manual cleanup. (RUNBOOK 11.7)
- **Provider object lock or versioning** and an **off-VPS heartbeat** are operator controls; nothing in the repository pings a monitor, so a failed backup unit is silent unless one is registered. (RUNBOOK 11.1, 11.4)
- **D050 records** that the `db-upgrade` one-shot's alembic logging is not wired through the redactor, and that redaction is value-based: new secret variables must keep a name containing PASSWORD, SECRET, TOKEN, API_KEY, ACCESS_KEY, CRYPT or PRIVATE.
- **`postgresql-client-17`** in the ops image floats within major 17 on purpose (the single exception to exact pins). (RUNBOOK 16)
- **Windows copies:** git warns that LF will become CRLF here; copy `deploy/` to a host from a clean checkout or `git archive`, not from an older Windows tree. (RUNBOOK 13.2)
- **`src/risk/portfolio.py` (user-facing flag, not fixed here):** `check_portfolio` computes `warning_threshold_quote` and `stop_threshold_quote` and never reads them (silenced by a per-file F841 ignore), and when `daily_loss_quote is None` the derived daily state is `NORMAL`, so the DAILY_STOP gate does not trigger on an unknown daily loss. That may be a fail-closed gap against the project rules; whether any live caller can pass `None` was not investigated. Recorded in D050 item (i).

- **Sudo-rsync migration fallback** is documented as unscripted and untested (RUNBOOK 15.3).
