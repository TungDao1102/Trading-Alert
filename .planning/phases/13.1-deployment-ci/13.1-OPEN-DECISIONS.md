## WR-05: who administers the host after hardening

`bootstrap.sh` sets `PermitRootLogin no`; the `trading` user is only in the `docker` group, with no
sudo. On a root-only VPS image, after bootstrap nobody can SSH in as root or run root-only commands
(`backup.sh --install-timer`, `apt`, `ufw`, `systemctl`) except through the provider console or a
docker escape.

Done so far (commit da1a0bc): wording only. The checklist and RUNBOOK 13.5 now say to install the timer
as root from the console or the bootstrap root session before closing it. Script behaviour is unchanged.

Options:
- `trading` joins `sudo`, optionally with NOPASSWD limited to bootstrap, backup and systemctl. Admin over
  SSH works; the `trading` SSH key becomes effectively a root key.
- `PermitRootLogin prohibit-password`: root keeps key login. Simple; root stays reachable over SSH.
- Leave as is and always use the provider console.

Reviewer leaned towards sudo with a limited scope. Not decided.

## WR-06: one shared `env_file` for every container

`docker-compose.yml:18` gives every service (collector, db-upgrade, paper, live, backup, ops) the whole
`.env`. The internet-facing, always-on collector therefore holds `BACKUP_S3_SECRET_ACCESS_KEY`,
`BACKUP_CRYPT_PASSWORD*`, `TELEGRAM_BOT_TOKEN` and, once uncommented, `BINANCE_LIVE_API_*`. One RCE or
debug dump in the collector would expose the backup crypt key and the trading key together.

Not fixed because it needs a closed list of the variables each service reads (the collector uses
pydantic settings, so grepping `os.environ` is not enough) and a docker re-check of every service, the
cutover test and the drills. No minimal safe variant exists.

Suggested design: per-service allowlists. collector and db-upgrade get `POSTGRES_*`, `OI_*`; backup and
ops get `BACKUP_*`; paper gets `TELEGRAM_*` and `BINANCE_TESTNET_*`; live gets `BINANCE_LIVE_*` from a
separate file.

Related: the `.env.example` sentence "a paper process can never pick up a live credential" is only true
of the variable names today. Soften it until this is decided. Also referenced from ROADMAP Phase 24.

## CR-01: `--size-only` on the Parquet push

Defect (fixed in 127a322 and b490be0): after a restore, files got new mtimes and
`rclone copy --immutable` failed every scheduled backup. The fix keeps mtime on restore (`copy2`) and
adds `--size-only` to the Parquet push.

Trade-off to confirm: a same-size file with different content at the same remote path is now skipped
silently at push time. Reasoning for accepting it: Parquet paths are append-only and the manifest
sha256 is checked on pull, so corruption would surface at restore, not at push. Alternative: use
`--checksum` instead (slower, hashes every file). Not decided; the fix stays in meanwhile.
