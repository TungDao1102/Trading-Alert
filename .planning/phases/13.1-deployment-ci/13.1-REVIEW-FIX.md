## Fixed Issues

### CR-01: After a restore, every scheduled backup fails with "immutable file modified"

**Status:** fixed (logic fix, requires human verification of the `--size-only` trade-off)
**Files modified:** `src/ops/backup.py`, `src/ops/backup_remote.py`, `tests/test_backup_remote.py`,
`tests/test_backup_restore.py`, `tests/test_docker_backup_remote.py`
**Commits:** `127a322` (fix + unit tests), `b490be0` (real-rclone docker test)
**Applied fix:** `_copy_into_target` uses `shutil.copy2` so a restored file keeps its original
mtime, and `push_snapshot` passes `--size-only` next to `--immutable` so the push compares size, not
modtime (the manifest sha256 already proves content). A same-named file of a different size is still
an error.
**Tests added:** the `StoreRclone` fake now models mtime (rclone's default size+modtime compare, strict
under `--immutable`, preserved on upload and download). New: push after a staged-mtime change,
backup -> push -> pull -> restore -> backup -> push, restore preserves mtime, plus a docker test
(`test_push_after_a_restore_with_new_mtimes_succeeds_with_the_real_rclone`). Reproduced first: the
unit tests failed before the fix; the docker test fails with "immutable file modified" when
`--size-only` is removed and passes with it.
**Note:** `--size-only` means a same-size, different-content file at the same remote path would be
skipped silently. Remote Parquet paths are date-partitioned and append-only and the pushed manifest
hashes are checked on pull (`verify_bundle`), so this was judged acceptable; flagged for the operator.

### WR-01: Retention and "newest" pull treat a half-pushed snapshot as the newest

**Status:** fixed: requires human verification (retention logic)
**Files modified:** `src/ops/backup_remote.py`, `tests/test_backup_remote.py`,
`tests/test_backup_retention.py`, `tests/test_docker_backup_remote.py`
**Commit:** `90311f3`
**Applied fix:** new `list_complete_snapshots` (one `rclone lsf --files-only -R --max-depth 2` of
`snapshots/`, ids that have a `manifest.json`). `pull_snapshot` picks the newest complete snapshot
(and refuses an explicitly named incomplete one). `apply_retention` runs `select_retained` over
complete snapshots only, purges an incomplete directory only when it is older than the newest
complete snapshot, and leaves a newer incomplete one alone (it may be a push in progress).
**Tests added:** pull skips a half-pushed newest snapshot; retention keeps the complete snapshot
over a same-day half push; retention purges stale incomplete directories; fake-runner variants in
`test_backup_retention.py`; the real-rclone docker test now exercises the recursive listing, the
pull fallback and the garbage purge.

### WR-04: Backup runs are not mutually exclusive

**Status:** fixed
**Files modified:** `src/ops/backup.py`, `tests/test_backup_lock.py` (new)
**Commit:** `a04e6a6`
**Applied fix:** `backup_lock(bundle_root)`: non-blocking exclusive lock (`fcntl.flock`, `msvcrt` on
Windows) on `<bundle parent>/.backup.lock`, held by `backup`, `push`, `scheduled` and
`drill-remote`. The lock sits on the shared volume, so it also serialises runs in different
containers. A second run fails with "another backup is already running". The lock file is excluded
from `write_manifest` and `verify_bundle`. The CLI dispatch was split into `_run_cli` (parse + lock)
and `_dispatch` (unchanged body).
**Tests added:** second holder refused then released; distinct roots independent; `backup`, `push`,
`scheduled`, `drill-remote` exit 1 with no rclone call while locked; lock file not in a manifest.
