# Phase 13.1: Code Review Report

**Reviewed:** 2026-10-04
**Depth:** deep (script-to-script flow: bootstrap -> compose -> backup/restore/migrate/update -> src.ops.*)
**Files Reviewed:** 62 (shell, compose, Dockerfile, workflows, src/ops, tests; the formatting commit 0060156 excluded)

## Summary

The phase is carefully built: no secret reaches argv (PGPASSWORD / RCLONE_CONFIG_* travel in the child
environment only), scripts pass `bash -n` and shellcheck 0.11.0, every action SHA and image digest in
the workflows, Dockerfile and compose file matches its tag (checked live with `git ls-remote` and
`deploy/refresh-pins.sh --lookup`: all 5 actions and all 4 images "unchanged"), retention is a pure
function that only ever purges `snapshots/<valid id>`, and the restore path refuses non-empty targets
before any destructive step.

Two things need action before this ships:

1. A disaster-recovery defect that makes every scheduled backup fail on a host that was restored
   from a backup (CR-01). Reproduced against the pinned rclone image.
2. A group of safety-net gaps around the same backup/rollback machinery (retention keeps an
   incomplete snapshot over a good one, rollback state is overwritten on a retried update,
   `migrate.sh` is broken for a remote new host, unprotected concurrent backups).

The unexplained `test_backfill_cli` flake did not reproduce: 75 consecutive in-process runs of
`test_cli_prints_depth_in_run_header` on HEAD passed (the recorded rate was 1 in 15 to 30, so the
chance of that by luck is about 2 percent). See WR-10 for the likely cause and the diagnosability
defect that made it unexplainable.

## Critical Issues

### CR-01: After a restore, every scheduled backup fails with "immutable file modified" (restored files get new mtimes)

**File:** `src/ops/backup.py:692-704` (`_copy_into_target`, `shutil.copyfile`), `src/ops/backup.py:257`
(`copytree` in staging), `src/ops/backup_remote.py:315-316` (`rclone copy ... --immutable`)

**Issue:** `restore_bundle` writes each Parquet file with `shutil.copyfile`, which does not preserve
the modification time. The next `backup()` stages them with `shutil.copytree` (copy2, mtime
preserved), so the staged files carry the restore time. `push_snapshot` then runs
`rclone copy <staged parquet> crypt:parquet --immutable`. The remote already holds the same files
(same size, same content, original mtime). rclone's default comparison is size plus modtime, and with
`--immutable` a modtime mismatch is an error, not a skip.

Reproduced with the pinned image (`rclone/rclone@sha256:45401ad7...`), local backend, identical
bytes, mtimes months apart:

```
rclone copy /w/src /w/dst --immutable
NOTICE: Failed to copy: immutable file modified
```

Failure scenario (the whole point of D-13): the VPS dies, the operator runs `deploy/restore.sh`, the
stack comes up, the 03:15 timer fires, `scheduled` raises `RemoteError` at `push_snapshot`, and it
does so every night afterwards. The new host has no off-host backups until someone diagnoses an
rclone error. A second failure in that window loses everything collected since the restore. The
oracle test double (`tests/test_backup_remote.py:486-491`) models "immutable" as a content
difference only, and no test runs a push after a restore, so nothing covers it.

**Fix:** preserve the bundle file's mtime on restore, and make the immutability check independent
of mtime.

```python
# src/ops/backup.py::_copy_into_target
shutil.copy2(src, tmp)            # keeps st_mtime of the pulled (originally collected) file
```
```python
# src/ops/backup_remote.py::push_snapshot  (the manifest sha256 already proves content)
_call(runner, ["copy", str(root / PARQUET_DIR), _crypt(PARQUET_DIR), "--immutable", "--size-only"])
```
Add a docker-marked test: backup, push, restore into an empty project, backup again, push again must
exit 0.

## Warnings

### WR-01: Retention and "newest" pull treat a half-pushed snapshot as the newest, and can delete the good one

**File:** `src/ops/backup_remote.py:364-368` (`max(parseable)`), `416-454` (`select_retained`),
`466-490` (`apply_retention`)

**Issue:** `push_snapshot` uploads `pg.dump` then `manifest.json` last, so a crash between the two
leaves `snapshots/<id>/pg.dump` without a manifest. Nothing checks completeness:
- `pull_snapshot(snapshot=None)` picks the newest id, hits `_read_manifest` -> "unusable", and
  `restore.sh` fails; the operator must know to pass `--snapshot` with an older id.
- `select_retained` keeps "the newest snapshot of each day". `update.sh`, `drill-remote` and manual
  runs all push a real snapshot, so two per day is normal. If the later one on a day is incomplete,
  the next scheduled run keeps it and deletes the complete earlier snapshot of that day (S1 is not
  retained by the weekly or monthly bucket when a newer snapshot exists in the same week or month).

**Fix:** in `list_snapshots` (or a new `list_complete_snapshots`) keep only ids whose
`snapshots/<id>/manifest.json` exists (`rclone lsf` the dir once per id, or `lsjson -R --max-depth 2`),
use that set for both pull and `select_retained`, and treat an incomplete dir older than a complete
one as garbage to purge only after a complete newer snapshot exists.

### WR-02: `update.sh --ref` overwrites the rollback state on a retry, making rollback a no-op

**File:** `deploy/update.sh:100-130` (`record_state` is called unconditionally at line 119)

**Issue:** `record_state` writes `GIT_SHA`/image IDs of whatever is current, then the script tags
`:rollback`. Run 1: state = (A, old images); checkout B; build succeeds (tags `:dev` -> new images);
`up -d` fails (migration error, bad `.env`). Operator fixes and re-runs `update.sh --ref B`: HEAD is
now B and `:dev` is the new image, so state becomes (B, new images) and `:rollback` is retagged to
the new image. `--rollback` now "rolls back" to the broken release; the last good release (A) is
gone.

**Fix:** refuse to re-record when a state file exists and `git rev-parse HEAD` equals the target
commit (or when `:dev` no longer equals the recorded `OPS_IMAGE_ID`/`APP_IMAGE_ID` and HEAD differs
from the recorded `GIT_SHA`): either "already at REF, nothing to record" or require
`--force-rerecord`. Keep the last state as `last-good.env.prev`.

### WR-03: `migrate.sh` cannot work with a remote `<new-ssh-target>` (arguments lose quoting through ssh)

**File:** `deploy/migrate.sh:125-133` (`NEW_COMPOSE=(ssh ... "$NEW_TARGET" docker compose ...)`),
`157-163` (`rsync_pull`)

**Issue:** the usage text advertises `<new-ssh-target|local>`. With a remote new target the whole
command is joined by ssh with spaces and re-parsed by the remote shell. `--rsync-path="$RSYNC_PATH"`
(contains spaces: `docker run --rm -i -v ...`) and `-e "$RSYNC_SSH"` (`ssh -i /keys/... -o ...`) are
split into separate words, so rsync receives `--rsync-path=docker` plus stray tokens and fails after
the old collector has already been stopped (step 3). The unquoted `--exclude '.*.tmp'` is also
globbed against the remote home directory. `--key-source` is also resolved on the remote host, not
the operator's machine, and the key-file preflight (line 172) only runs for `local`. The test suite
only drives the `MIGRATE_NEW_COMPOSE` harness, never this branch.

**Fix:** either reject a non-`local` new target in `parse_args` ("run this script on the new host"),
which matches the safer documented flow, or build the remote command with `printf '%q '` for every
word before handing it to ssh, and extend preflight to the remote key source.

### WR-04: Backup runs are not mutually exclusive (shared staging directory, second-resolution snapshot id)

**File:** `deploy/backup.sh:64-66,104`, `src/ops/backup.py:249-260`, `deploy/systemd/trading-backup.timer:5-8`

**Issue:** every `scheduled` run does `rmtree(data/backup/bundle/parquet/raw)`, `copytree`, then
rewrites `manifest.json` in the same directory. `update.sh` runs `backup.sh`, `backup-drill.sh`
pushes through the same bundle, and the timer fires with `RandomizedDelaySec=5m` and
`Persistent=true`. Two overlapping runs make each other's `verify_bundle` fail (best case, a failed
run) or race between verify and push. Nothing serialises them.

**Fix:** wrap the python invocation in `flock -n /var/lock/trading-backup.lock` (or hold an
`fcntl.flock` on `data/backup/.lock` inside `src.ops.backup`) and fail with a clear "backup already
running".

### WR-05: Bootstrap hardens SSH to "no root login" but leaves no privileged path, and the checklist then needs root

**File:** `deploy/bootstrap.sh:219-241` (`step_user`: `useradd` + `usermod -aG docker` only),
`284-291` (`PermitRootLogin no`), `517-518` (checklist: run `backup.sh --install-timer`)

**Issue:** on a root-only VPS image (common: Hetzner, many Debian images) the operator ran bootstrap
as root. Afterwards root cannot log in, `trading` is not in `sudo`, and `backup.sh --install-timer`
(line 69-71) dies with "must run as root". Any later `apt`, `bootstrap.sh` re-run, `ufw` change or
`systemctl` needs the provider console. The lock-out guard only proves a key exists for `trading`,
not that someone can administer the host afterwards. The checklist item 7 says the docker group is
root-equivalent, so the only admin path is a docker escape.

**Fix:** add a preflight/step that either adds `trading` to `sudo` (with a documented NOPASSWD scope
limited to bootstrap/backup/systemctl) or sets `PermitRootLogin prohibit-password` and keeps root's
key. At minimum, change checklist item 6 to the command that actually works and state how root is
reached.

### WR-06: Single shared `env_file` hands backup, Telegram and (future) live credentials to every container

**File:** `docker-compose.yml:18` (`x-app` env_file), used by `collector`, `db-upgrade`, `paper`,
`live`, `backup`, `ops`

**Issue:** the always-on `collector` (internet-facing HTTP client, parses exchange payloads) gets
`BACKUP_S3_SECRET_ACCESS_KEY`, `BACKUP_CRYPT_PASSWORD*`, `TELEGRAM_BOT_TOKEN` and, once uncommented,
`BINANCE_LIVE_API_*`. `.env.example` claims "a paper process can never pick up a live credential by
accident", but with one env file both sets sit in the `paper` container's environment; only the
variable names differ. Any RCE or debug dump in the collector exposes the backup crypt key and the
trading key together.

**Fix:** per-service allowlists: `collector`/`db-upgrade` get only `POSTGRES_*`, `OI_*`; `backup`/`ops`
get `BACKUP_*`; `paper` gets `TELEGRAM_*`, `BINANCE_TESTNET_*`; `live` gets `BINANCE_LIVE_*` from a
separate file. Use `env_file:` per service (several files allowed) or explicit `environment:` keys
with `${VAR:-}`.

### WR-07: `.gitignore` ignores only `.env` and `.env.local`

**File:** `.gitignore` (lines 35-37)

**Issue:** `.dockerignore` correctly excludes `.env.*` (except the template), but `.gitignore` does
not. The new operator flow encourages variants (`--secrets-file`, `TRADING_ENV_FILE`, a live
deployment's "own .env"). `.env.prod`, `.env.live` or `.env.backup` are untracked-but-addable and
`git add -A` commits real credentials (the project rule is "credentials must never be in git").

**Fix:**
```
.env
.env.*
!.env.example
```
and add `*.pem`, `id_ed25519*`, `secrets*.env`.

### WR-08: Three of four workflows run with the repository default token permissions

**File:** `.github/workflows/registry-gate.yml:1-12`, `research-gate.yml:1-12`,
`paper_freeze_check.yml:21-30` (no `permissions:`; only `ci.yml:14` sets `contents: read`)

**Issue:** `tests/test_deploy_workflows.py:65-71` enforces least privilege for `ci.yml` only. If the
repository default is "read and write" (the GitHub default for older repos), `registry-gate` runs
`uv run` of PR code with a write-capable `GITHUB_TOKEN`, and `actions/checkout` persists it in
`.git/config`. The scheduled `paper_freeze_check` (cron, default branch) does the same hourly.

**Fix:** add to each file (and extend the workflow test to loop over all four):
```yaml
permissions:
  contents: read
```
`actions/cache` and `upload-artifact` use the runtime token, not `GITHUB_TOKEN`, so nothing else is
needed. Add `persist-credentials: false` to the checkout steps.

### WR-09: `test_research_gate_negative.py` skips at module level, bypassing the strict CI mode

**File:** `tests/test_research_gate_negative.py:30-32`

**Issue:** the phase introduced `infra_skip` precisely so a missing tool fails under
`TRADING_CI_STRICT=1`, but this module calls `pytest.skip(..., allow_module_level=True)` directly.
Also `registry-gate.yml` runs this file without `TRADING_CI_STRICT` and without `-rs`, so a skipped
gate test is invisible in that job. If bash is ever absent from the runner image, the research-gate
negative tests vanish and the job is green.

**Fix:**
```python
BASH = find_bash()
if BASH is None:
    from tests.infra_helpers import STRICT_ENV
    if os.environ.get(STRICT_ENV) == "1":
        raise RuntimeError("bash is required (TRADING_CI_STRICT=1)")
    pytest.skip("bash is required ...", allow_module_level=True)
```
and set `TRADING_CI_STRICT: "1"` plus `-rs` in `registry-gate.yml`.

### WR-10: `backfill_cli.main` discards the failure cause, which is why the flake is unexplainable

**File:** `src/data/backfill_cli.py:1183-1187`; related `src/data/backfill_cli.py:547-561`

**Issue:** the generic branch prints only `type(exc).__name__` and logs only `error_type`. The stated
reason ("a database error message can embed the connection URL") stopped being true when this same
phase added `redact_processor` (13.1-04) and `configure_logging()` is called at line 1144. So the
`rc == 1` flake recorded in `deferred-items.md` has no recoverable cause in any log.

Likely cause: the flake was recorded on 2026-10-01 on Windows; the cursor-file `os.replace`
`PermissionError` retry landed two days later (`413e0e6`, 2026-10-03). 75 consecutive runs on HEAD
passed. One unprotected `os.replace` remains on a path of this CLI: `_save_archive_presets`
(`backfill_cli.py:556-561`, no retry, and a fixed `.tmp` name without pid) would raise the same way
on Windows when an archive-sourced symbol is saved.

**Fix:**
```python
except Exception as exc:
    print(f"backfill: failed ({type(exc).__name__})", file=sys.stderr)
    log.exception("backfill.failed")   # traceback goes through redact_processor
    return 1
```
and reuse the `REPLACE_MAX_ATTEMPTS` retry loop (or a shared `atomic_replace` helper) in
`_save_archive_presets`. Then close the deferred item with this evidence.

### WR-11: `validate_secrets_file` does not enforce what compose and the redactor silently depend on

**File:** `deploy/bootstrap.sh:441-485`, `docker-compose.yml:33-37`, `src/ops/redaction.py:73`

**Issue:** compose builds `DATABASE_URL=postgresql+psycopg://user:${POSTGRES_PASSWORD}@postgres/...`
and states "Passwords must stay URL-safe", but bootstrap only checks "non-empty and no change_me".
A password with `@`, `/`, `:` or `#`, or with `$` (compose interpolation) passes validation and
produces a stack that never connects (the collector and `db-upgrade` fail; at best fail-closed, but
discovered after the SSH hardening step). Also any `POSTGRES_PASSWORD` shorter than
`MIN_SECRET_LENGTH = 8` is never value-redacted outside URL shapes.

**Fix:** in the awk validator add: `POSTGRES_PASSWORD` must match `^[A-Za-z0-9._~-]{16,}$`
(or at least `{8,}`), else report "key name only". Run this check in `preflight`, which already runs
before any mutation.

### WR-12: `.dockerignore` patterns only match at the build-context root; 195 host `.pyc` files are baked into the image

**File:** `.dockerignore:25-26` (`__pycache__`, `*.py[cod]`)

**Issue:** `.dockerignore` patterns are anchored to the context root, so `src/**/__pycache__` is not
excluded. Verified in the locally built image: `find /app/src /app/scripts -name '*.pyc'` -> 195
files (`/app/src/execution/__pycache__/intent_store.cpython-313.pyc` etc.). The image is then not a
function of the repository: it depends on whatever bytecode the build host had, and the layer carries
host paths in `co_filename`. This conflicts with the "pinned, reproducible image" intent of D-05.

**Fix:**
```
**/__pycache__
**/*.py[cod]
**/.pytest_cache
```

### WR-13: Destructive default ordering when ufw is already active (allow rule added after default deny)

**File:** `deploy/bootstrap.sh:271-276`

**Issue:** the idempotency check treats ufw as non-compliant if any SSH allow rule is missing and then
runs `ufw default deny incoming` before `ufw allow <port>/tcp`. On a host where ufw is already active
(re-run, or a second SSH port), new SSH connections are dropped between the two commands, and
permanently if `ufw allow` fails (`set -e` aborts after the deny took effect). Established sessions
survive via conntrack, so this is a window rather than a guaranteed lock-out.

**Fix:** reorder to `allow` first, then `default deny incoming`, then `enable`.

## Info

### IN-01: `install_timer` substitutes the checkout path with an unquoted replacement (bash 5.2 `&` is special)

**File:** `deploy/backup.sh:78`
`content="${content//"$UNIT_TOKEN"/$REPO_ROOT}"` turns a checkout under `/opt/a&b` into
`/opt/a@TRADING_DIR@b` (reproduced on bash 5.2.37). Quote the replacement: `/"$REPO_ROOT"`.

### IN-02: systemd unit hard-codes `User=trading` while `bootstrap.sh --user` is configurable

**File:** `deploy/systemd/trading-backup.service:11`, `deploy/bootstrap.sh:26`
A bootstrap with `--user ops` installs a timer whose service fails to start ("Failed to determine
user credentials"). Add a `@TRADING_USER@` token substituted from the checkout owner.

### IN-03: Docker apt key is trusted on first fetch; no fingerprint pin (the Dockerfile pins the PGDG one)

**File:** `deploy/bootstrap.sh:196-199`
Same standard as the PGDG step in `Dockerfile:68-72` would be consistent: check
`gpg --show-keys --with-colons` against Docker's published fingerprint before writing the sources
file. Related: `step_checkout` uses `StrictHostKeyChecking=accept-new` (line 420) and a mutable tag
as `--ref`; document that `--ref` should be a commit SHA.

### IN-04: `--ref` / `--rollback` semantics for a branch name

**File:** `deploy/update.sh:125-126`, `deploy/bootstrap.sh:431-438`
`git checkout --detach master` resolves the possibly stale local branch, not `origin/master`, after
`git fetch`. Resolve explicitly with `git rev-parse --verify "$REF^{commit}"` after the fetch and
refuse a ref that is a local branch name.

### IN-05: Plaintext copies of production data accumulate in the backup volume

**File:** `deploy/restore.sh:79`, `deploy/backup-drill.sh:56-58`, `deploy/migrate.sh:207`,
`src/ops/backup.py:249-257`
`data/backup/bundle` (full plaintext pg.dump plus a second copy of the whole Parquet store, recreated
each night), `restore-<ts>`, `drill-<ts>` and `cutover/pg.dump` stay on the host unencrypted and are
never cleaned. Encryption at rest rests entirely on provider disk encryption (checklist 5). Add a
`--cleanup` or a retention for `restore-*`/`drill-*`, and delete `cutover/` after a clean report.

### IN-06: `drill-remote` verifies only `collector_watermarks` row counts, taken at different times

**File:** `src/ops/backup_remote.py:701-723`
The source count is read after the dump while the collector keeps inserting, so a healthy drill can
fail spuriously, and equal counts prove little about the restore. Compare the sha256 of an ordered
dump of `(symbol, data_class, last_tick_utc)` from the scratch DB with the same rows read from the
dump's own `pg_restore -f -` listing, or stop the comparison from racing by also recording the count
inside the same `pg_dump` snapshot.

### IN-07: `migrate.sh` names the old host's image with the operator's `IMAGE_TAG`

**File:** `deploy/migrate.sh:136`
`trading-alert-ops:${IMAGE_TAG:-dev}` is evaluated on the machine running the script, but the image
runs on the old host. If the old host runs `v1.2`, `docker run` tries to pull `:dev` and the pre-sync
fails (fail closed, but confusing). Take the tag from a `MIGRATE_OLD_IMAGE_TAG` variable.

### IN-08: Stale documentation of the old backup design

**File:** `src/ops/backup.py:32-39` (`BACKUP_TARGET`, OneDrive agent), `.env.example`
(`OFF_HOST_BACKUP_TARGET=data/backup`, "OneDrive-synced dir")
The real off-host design is rclone S3 + crypt (`BACKUP_S3_*`). Neither variable is read by the new
code. Remove them so an operator does not believe a local directory is an off-host backup.

### IN-09: Dead code and a misleading lint waiver

**File:** `pyproject.toml:81-85`, `src/risk/portfolio.py:302-303`
The waiver says the unused `warning_threshold_quote` / `stop_threshold_quote` "may be a latent
daily-loss gating gap". It is not: the daily state is derived at lines 243-246 and `DAILY_STOP`
blocks at line 348. Delete the two dead assignments and the `F841` ignore instead of carrying a
warning that implies a risk hole. (`tests/fixtures/cutover/Dockerfile.sshd` also lost its `\`
continuations: the RUN is one 300-char line of padding spaces; harmless but unreadable.)

### IN-10: Gating and hardening notes

- `ci.yml:8-12` triggers on pushes to `master` only; the active branch is `develop`, so direct pushes
  there are ungated (PRs to master are gated). `concurrency.cancel-in-progress: true` also cancels
  the run of a previous master commit when two land quickly.
- `ci.yml` pins the postgres service image digest separately from `docker-compose.yml`;
  `refresh-pins.sh` (`image_pins`, lines 57-63) does not read `ci.yml` or `tests/docker_helpers.py`,
  so a bump can leave them behind (only tests catch that).
- `docker-compose.yml` services run without `security_opt: [no-new-privileges:true]`,
  `cap_drop: [ALL]` or `read_only: true`; the app does not need any capability.
- `src/ops/redaction.py:176-178` masks any log key containing `token`/`signature`, including
  non-secret diagnostics such as `token_hash` in approval lineage; consider an allowlist for
  `*_hash`/`*_count`. Values shorter than 8 characters are never value-redacted (see WR-11).
