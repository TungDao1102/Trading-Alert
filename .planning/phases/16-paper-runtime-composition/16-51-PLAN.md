<objective>
Close gap 16-25 D6 under the user's decision `decisions/16-DEC-PARITY.md` (option 1, locked: the runtime records the replay inputs; option 2, a narrower parity, is not planned). Parity with tolerance zero (D061 item D, L-04) is NOT EVALUATED on a real bundle because the bundle holds the bar and the surface but not what the risk stage read. This plan makes the runtime record, per evaluated live bar, the constraint snapshot it used, the account state, the open positions and daily loss the risk-inputs port returned at the close and the ttl, and makes the evaluator rebuild the replay from the bundle and nothing else.

Planner finding, inside option 1 (not a new option): the bundle also lacks the history the live windows were cut from. `ParityReplay.history_bars` (plan 16-25) are "the REST warm-up bars the runtime loaded before its first live bar", and REST_WARMUP, REST_BACKFILL, restart-fenced and fetched 4h sibling bars are never recorded today. The live windows also depend on the ORDER in which bars entered the buffers: a bar backfilled after a later live bar was absent from that bar's window. So the pipeline logs every bar it accepts into its history, live ones included, with its acceptance sequence `accept_seq`, each replay-inputs record names `window_accept_seq`, and the replay rebuilds every window from its run's log in acceptance order, one process run at a time.

Record design (with the reason): two NEW record types written through the same `RuntimeStatePort.record` (idempotent replay, epoch-scoped ids, Q-J journal-only, no migration, D-04): `PAPER_REPLAY_INPUTS` (bar-keyed like the heartbeat) and `PAPER_HISTORY_BARS` (keyed on tick time and a per-pipeline sequence like PAPER_TICK_STATS). Extending the PAPER_BAR_PROCESSED payload was rejected: (1) neither option moves a sha256 digest (no pinned digest covers the heartbeat payload; see the digest review), so digests do not decide; (2) the heartbeat is the coverage record read by `src/paper/coverage.py`, by the restart (`last_close_by_pair`) and field by field by the 16-24 tests, and keeping it byte-identical leaves every consumer and assertion untouched; (3) only evaluated bars have a context, so an extended heartbeat would carry nulls on every gate and context record; (4) a changed heartbeat payload changes the content behind an existing id, which `RuntimeRecordConflict` refuses on any replay of a record written by an earlier build, while a new event type gets new ids; (5) the history log needs a new type in either option. Both options move the same three non-digest pinned expectations, so the separate type moves no more pins and changes no existing record.

Not in this plan: the cross-epoch EPOCH_PINNED check (gap 16-29 deviation 1) is plan 16-52.

Output: the recording, the run-by-run replay from the bundle, the line writer and command line, the pin review file and (only after the user approves the review) the re-pinned expectations.
