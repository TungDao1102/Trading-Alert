### Confirmed in code (read 2026-11-08)

Two code paths use two different equity bases:

- **Signal time, the bar pipeline** (`src/paper/market_inputs.py:185-188`): the account state
  (`AccountState(equity=account.initial_equity, ...)`) and the absolute portfolio thresholds
  (`resolve_absolute_thresholds(..., equity=account.initial_equity)`) both use the configured
  `initial_equity` (600). It never changes with realized PnL. The sized risk is about
  0.005 x 600 = 3.0 and the pipeline cap is 3.0, so the signal passes and the alert is sent.
- **Confirm time, the SHADOW ledger** (`ShadowLedger.admit` in `src/paper/shadow_ledger.py`, over
  `ledger.thresholds` of `src/backtest/ledger.py`): the thresholds are re-resolved against the
  ledger equity at each UTC day start (`_resolve_thresholds`, `roll_to`), i.e. 600 plus the
  realized bookings. After the four losses the cap is 0.005 x 592.61 = 2.963, below a sized risk
  of 2.99877, so `check_portfolio` returns CLUSTER_CAP_REJECT with no position open.

The backtest engine sizes with the ledger equity too (`src/backtest/engine.py:751` and `:858`,
`AccountState(equity=self.ledger.equity, ...)`), so sizing and cap use one base there. The paper
runtime copied the ledger for the thresholds but sizes with the constant initial equity; it differs
from the simulator that the project treats as canonical.

Consequence: once ledger equity falls below about 599.75, a standard candidate is rejected at
confirm even with an empty book. A candidate whose quantization leaves the risk well below the
allowed amount can still pass until equity falls further. Every aggregate and daily-loss threshold
has the same mismatch (same helper), so the effect is not limited to the cluster cap.

### Explained by the code (read 2026-11-08)

Three different quantities exist for one plan:

1. **Planner** (`src/core/planner.py:615-638`, `:713-717`): `entry_ref` is the zone mid and
   `risk = |entry_ref - stop_loss|`; `suggested_quantity = (equity x risk_rate) / risk` is stored as
   `TradePlan.quantity_after_rounding` ("Phase 5 floors; planner passes through"). For the XRP plan
   this is 476.27, i.e. 3.0 / 0.0063 per unit.
2. **Risk stage** (the `risk.quantize` log): sizes on the adverse edge of the zone (entry
   1.250375790, stop distance rate 0.008815874, so 0.011023 per unit) plus modeled costs of
   0.001827 per unit, giving 0.01285 per unit and 3.0 / 0.01285 = 234.6 with a realized risk of
   2.99877. This is the quantity the ledger reserves (`_basis_for` in `shadow_runtime.py`) and the
   one the simulated fill reads.
3. **Confirm card** (`render_confirm_card`, `src/paper/shadow_confirm.py:143-181`): shows
   `plan.quantity_after_rounding` (the planner's 476.27) and computes
   `estimated_loss = quantity x |entry_ref - stop_loss|` with `entry_ref` at the adverse edge,
   0.011023 per unit, which gives 5.25.

So the card mixes the planner quantity (sized on the zone mid, no costs) with the adverse-edge
distance. It is a display defect: the number on the card is not the quantity that is simulated.
The simulated risk is the checked one (about 3.0). The same planner quantity is the
`approved_quantity` that the approval rows and the live path bind (`approval_desk.py`); a placement
may be smaller than approved, never larger, so the live rule holds, but the figure the operator
sees is not the one that would be placed.
