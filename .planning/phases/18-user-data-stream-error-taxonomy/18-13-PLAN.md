<objective>
Make the recvWindow explicit and the clock-drift decision effective on the Binance signed-call surface (D-14, F-505, F-706, F-128): one helper carries `recv_window` to the SDK for all eleven signed methods, a missing policy fails closed, a `-1021` answer notifies a hook and is never retried, and a configured `ClockDriftGuard` stops NEW entries (not protective orders, cancels or reads).

Purpose: nothing passes `recv_window` today, so the exchange default of 5000 ms applies silently and the signing clock is the host clock; an unratified default must not decide replay-window width. Blocking new entries on a failed or stale server-time measurement is the fail-closed outcome the roadmap asks for.
Output: the adapter refactor, the matrix tests, the updated existing tests and the rehearsal policy loading.

Out of scope: composing the guard's refresh loop into a process (Phases 19 and 24), unsigned public calls (`binance_public.py` has no recvWindow; its timeout comes from the client configuration of plan 18-04), the manager's reaction to `EntriesBlocked` (Phase 19).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host clock -> signed request timestamp | A skewed host clock makes signed requests fail or widens the replay window |
| new-entry order path | A new entry on a skewed or unmeasured clock is the risky action |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-----------|-----------------|
| T-18-36 | Tampering | signed requests using the exchange default recvWindow (replay window chosen by nobody) | high | mitigate | One helper forwards the ratified recv_window on all eleven signed methods; a missing policy raises before any SDK call; matrix and signature-binding tests |
| T-18-37 | Tampering | automatic retry of an order after -1021, or a new entry sent on an unmeasured, failed, out-of-limit or stale clock | high | mitigate | -1021 only calls the hook and re-raises, never retried (cancel retry excludes CLOCK_SKEW); place_entry refuses through EntriesBlocked when the guard blocks; protective orders and cancels are never blocked |
| T-18-38 | Denial of service | SDK retries stacking with project retries on the signed surface, or a 429 retried on a placement or read | medium | mitigate | The ratified client.sdk_retries governs the SDK layer; the helper never retries; the project cancel retry stays bounded by the existing ceilings and uses the user's 429 fallback; the stacking is documented in the O-18-01 table; the 429 matrix over the eleven methods |
| T-18-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed or changed in this plan |
</threat_model>
