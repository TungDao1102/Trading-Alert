## Semantics stated in the accepted text (binding on plans 18-05, 18-10, 18-13)

- HTTP 418 with a missing or unparseable Retry-After: block REST for the 418 fallback (259200 s); the failing request is not retried.
- HTTP 429 with a missing or unparseable Retry-After: apply the 429 fallback (120 s). Per the user's line, cancel and read calls may be retried only within the bounded existing retry (the four `_RECONCILER_CANCEL_*` constants), waiting the decision's wait; a call that places an order is never retried automatically.
- A valid Retry-After is honoured, capped by `signed_calls.rate_limit_retry_after_cap_seconds`.
- Waiting out a fallback proves nothing about an order's cancel, fill or the existence of a protective stop; the unresolved state stays fail-closed and goes through reconciliation. The end of a wait is not a basis to restore protection status or to allow new entries while account state is unknown.
- No ALGO_UPDATE status in TRIGGERING, TRIGGERED, FINISHED or CANCELED is ACTIVE: in the implementation ACTIVE is the basis of `is_protection_confirmed`, so these stay UNKNOWN until independently verified through Binance (D055 not decided here).
