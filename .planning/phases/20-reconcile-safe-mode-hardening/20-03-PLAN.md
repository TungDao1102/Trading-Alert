<objective>
Give reconciliation its own result API (T-B; correction 2 of the review). Today `record_result` takes status, exchange_order_id and exchange_status only, and the ENTRY row's outcome_* columns are already used by the manager on the ambiguous path, so "closed because reconciliation proved absence" cannot be recorded distinctly. This plan adds a dedicated, narrow finalization method and a nullable reason column, covered by one shared contract test for both stores.

Choice recorded (T-B asks the plan to choose and record why): option 2, a dedicated reconciliation-finalization API. Reasons: (1) record_result is the exchange-response contract used by the manager, the coordinator and recovery and by four test fakes; changing it touches every caller; (2) outcome_* cannot be reused (see the must_haves truth) [DOC]; (3) a single writer for the reason column keeps "who may conclude absence" auditable. Reversibility: costly (a nullable column with a real downgrade; the store Protocol gains a method every fake must implement).

Consumers: plan 20-10 (UNKNOWN-entry protocol, INTENDED path). Executor rules: `codegraph explore "ExecutionIntentStore record_result finalize_entry_outcome PgExecutionStateStore InMemoryExecutionIntentStore"` first; run only this plan's tests; `alembic upgrade head` only (never create_all); stage explicit paths; commit trailer = the model that did the work.
</objective>
