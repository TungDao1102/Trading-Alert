<objective>
The durable risk reservation (criterion 3, F-407, F-955, D-16, D-17): a `risk_reservations` table, a store with the reserve step that runs under a single row lock inside a caller's transaction, and explicit, conflict-checked lifecycle transitions including the release table for every terminal plan state.

Purpose: today the caps are checked on a caller-supplied snapshot with no lock and no reservation, so two concurrent approvals can both pass (F-407). The plan's risk is registered at issue time as a REQUESTED row (not counted) so the approval binds to the risk the operator saw; reserve_in flips it to RESERVED (counted) only if the shared gate passes inside the caller's transaction. Plan 21-15 composes reserve_in into the approval transaction (decide and reserve atomically) and proves the two-connection race; this plan delivers the table and the store.
Design choices (Claude's discretion per CONTEXT): a REQUESTED row instead of a new approvals column, so the Approval entity, its request identity (D078) and the PgApprovalStore used by paper SHADOW stay unchanged; the lock is `SELECT ... FOR UPDATE` on today's `daily_risk_days` row (one operator, one process; A6); release() keeps the first stored reason when a second terminal signal arrives for an already RELEASED row (two terminal signals can race, e.g. the approval expiry and the plan expiry of a PENDING plan; a RELEASED row cannot be counted again because mark_placed and mark_open on it raise RowConflict, which is where a real inconsistency surfaces).
Output: migration 0011, ORM row, store, PostgreSQL tests, pins and DATA_MODEL.
