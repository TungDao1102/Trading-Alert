## Why

`src/ops/backup_remote.py` (~lines 328-335) pushes Parquet with `rclone copy ... --immutable --size-only`. With `--size-only` a same-size file with different content at the same remote path is skipped silently at push time. The user decided to use `--checksum`. Trade-off the user accepted: slower (every file hashed), and a same-size changed file is no longer skipped silently. The mtime-preserving restore fix stays.

## Key risk the plan must put FIRST

The remote is an rclone crypt remote on S3. rclone docs say hashes are not stored for crypt. `--checksum` with no common hash between source and destination may silently fall back to something weaker, or do nothing useful. So before any code change the executor must PROVE with real rclone (the repo's pinned image in `tests/docker_helpers.py`, `DockerRclone`, `S3Double`):

1. A same-size, different-content file already on the crypt remote at the same path: with `--checksum --immutable` the push must ERROR ("immutable file modified" or equivalent), and the old remote content must stay unchanged.
2. An unchanged file, including after only its mtime changed, must be skipped with no error and no re-upload.
3. A new file must upload.

If (1) does not hold (the flag is a no-op on crypt), the executor STOPS: no change to `src/ops/backup_remote.py`, writes the finding into the SUMMARY with the rclone output, and lists the alternatives for the user to choose (for example keep `--size-only` and add `rclone cryptcheck` of parquet/ after the push, or hash locally against the manifest).
