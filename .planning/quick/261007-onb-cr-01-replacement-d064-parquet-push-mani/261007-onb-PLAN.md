<objective>
Implement D064 (docs/DECISIONS.md, accepted 2026-10-07, replaces D062 item 2): the Parquet push in `src/ops/backup_remote.py` (`push_snapshot`, about lines 308-339) decides content identity by SHA-256 against the manifests of the complete remote snapshots, never by rclone size, mtime or a checksum option, and verifies the result with `rclone cryptcheck` before `manifest.json` is published.

Why (evidence, quick task 261007-mv4, rclone 1.75.1, proof output kept in `.planning/quick/261007-mv4-cr-01-parquet-push-checksum/`): on a crypt remote the checksum option prints "--checksum is in use but the source and destination have no hashes in common; falling back to --size-only", and a same-size different-content file is skipped with exit 0; plain `--immutable` also skips it when the mtime is unchanged. So the premise of D062 item 2 was false and nothing was changed then. This plan is the replacement.

The design, in the order the push runs it:
1. verify the bundle locally (unchanged), check the sentinel (unchanged);
2. read the known set: the manifests of all complete remote snapshots (`list_complete_snapshots`, then `rclone cat` of each `manifest.json`) plus one recursive listing of `parquet/` (decrypted names);
3. classify every local Parquet path (the bundle manifest keys under `parquet/`): same hash known = skip; different hash known = hard failure, nothing uploaded, no overwrite; new to every manifest and absent from the remote = upload; new to every manifest but already on the remote = subset `cryptcheck`, adopt if identical (no upload), hard failure if different. A different size at the same path is the same hard failure;
4. upload only the "upload" subset (`copy` with `--files-from-raw`, still `--immutable`), then `pg.dump`;
5. `cryptcheck` of the whole Parquet tree (one-way) and of `pg.dump`; any failure ends the push with no manifest published;
6. publish `manifest.json`, `cryptcheck` it; on any failure of those two steps remove the just-published manifest object (`deletefile`, one retry) so the snapshot never looks complete.

Facts found while planning (verified by reading the repo on 2026-10-07):
- `backup()` stages Parquet into `{bundle}/parquet/{root basename}/...` with `copytree` (mtimes preserved), then writes `manifest.json` as a flat mapping `relative path -> sha256` (`write_manifest`, `json.dumps(sort_keys=True, indent=2)`, ASCII). `verify_bundle` requires a str-to-str mapping, hashes every file and demands set equality with the files on disk. `bundle_sha256` is the sha256 of that manifest file (D-12, reproducible). Remote Parquet paths therefore look like `raw/interval=1m/symbol=X/date=D/part.parquet` under `parquet/`.
- Parquet files are immutable per day by design (`src/data/store.py`: "Files are append/immutable. Republishing an existing file raises"), so a different hash at an existing path is an anomaly worth a hard failure, not a normal update.
- `prune_bundle` removes stale local files and rewrites the manifest; the remote `parquet/` tree is never pruned (`apply_retention` never touches it). Retention (7/4/6) purges old `snapshots/{id}` directories, so a surviving manifest set can forget a path that is still on the remote.
- `pull_snapshot` copies the whole `snapshots/{id}` directory and `verify_bundle` then rejects any extra file: a leftover temporary object inside a snapshot directory would break a restore. This is why the compensating step is `deletefile` of the manifest and not an upload-under-another-name plus rename.
- `list_complete_snapshots` already defines "complete" as "its manifest.json exists"; retention and pull already ignore directories without one.
- Existing tests that pin the old behaviour and must be changed deliberately (Task 2 lists each): `test_push_cli_runs_sentinel_then_parquet_then_snapshot_then_cryptcheck` (pins the full argv including the old flag), `StoreRclone._put` and `StoreRclone.__call__` (the `size_only` parameter), `test_push_never_issues_delete_sync_or_move_against_the_remote` (verb allow-list: the push now also issues `lsf` and `cat`, and `deletefile` only when compensating), `test_scheduled_runs_backup_verify_push_then_retention_in_order` (asserts the first `lsf` comes after the first `cryptcheck`; the push now lists first), `test_scheduled_stops_before_retention_when_cryptcheck_fails` (asserts `lsf` is absent from the whole run), `test_push_skips_parquet_copy_when_bundle_has_no_parquet`, `test_push_uploads_manifest_last_so_a_snapshot_is_never_complete_before_its_files`, `test_a_changed_parquet_file_makes_the_immutable_copy_fail` (a changed remote object is now detected by cryptcheck, not by exit 6), `test_push_fails_on_nonzero_exit_of_any_step_including_exit_3`.
- `src/ops/backup.py` is NOT edited: its restore comment about mtime stays true (the mtime-preserving restore stays per D064); `cli_push`, `cli_scheduled` and the drill call `push_snapshot` unchanged.

Decisions this plan takes (all reported to the user at the end; none changes D064, none sets a threshold or time limit):
- PD-1 KNOWN SET = union of the manifests of ALL complete remote snapshots PLUS one recursive listing of `parquet/`. The listing is used only for presence (a listing has no hashes); the manifests give hashes. Trade-offs (verified facts: `prune_bundle` forgets paths locally while `parquet/` is never pruned remotely; retention can purge the only snapshot naming a path):
  | Option | Reads per push | Knows | Forgets | Result |
  |--------|----------------|-------|---------|--------|
  | newest manifest only | 1 cat | hashes of the newest snapshot | paths pruned locally earlier, still on the remote | needs the listing to be safe |
  | union of complete manifests | 1 cat per complete snapshot (about 17 in steady state under 7/4/6, more if retention has not run) | the hash of every path published by a surviving snapshot | paths named only by purged snapshots | needs the listing to be safe |
  | listing only | 1 recursive lsf | presence only, no hash | nothing | every present path then needs a content read before upload, a second full cryptcheck per push |
  | CHOSEN: union plus listing | the union cost plus 1 lsf | hash where any surviving manifest knows the path, presence everywhere else | nothing: a remote path is named by a surviving manifest or appears in the listing | an unknown remote path is never overwritten: it is adopted after a content check or refused |
  Costs of the choice: more small reads per push and more memory for big trees (one manifest text at a time plus a path to set-of-hashes dictionary); an unreadable manifest of a complete snapshot is a hard failure (PD-2).
- PD-2 FAIL CLOSED on the known set: a complete snapshot whose manifest cannot be read, is not valid JSON, is not a str-to-str mapping or holds an unsafe key is a hard failure naming the snapshot id (ignoring it would silently shrink the known set); a path that two surviving manifests name with different hashes is a hard failure ("manifests disagree"), because it proves an earlier silent divergence.
- PD-3 NO AUTO-HEAL: a known path whose remote object is missing or altered is NOT re-uploaded by the push; the whole-tree cryptcheck fails and the operator decides (a deleted or altered backup object may be a security event; D064 asks for detection). The RUNBOOK says what to look at.
- PD-4 COMPENSATING STEP = `deletefile` of `snapshots/{id}/manifest.json` of the snapshot being pushed, attempted twice (one retry, idempotent), tolerating "not found" with exactly the exit codes Task 1 recorded. REJECTED alternative: upload under a temporary name and rename. Reasons: S3 rename is copy plus delete; a crash between them leaves a complete snapshot plus a leftover object that `pull_snapshot` copies into the bundle and `verify_bundle` then rejects ("in bundle but not in manifest"), breaking the restore of the newest snapshot; and the final-name object would still need its own check. The remaining windows are stated in RUNBOOK 11 (W1 to W5 below).
- PD-5 SNAPSHOT-ID COLLISION GUARD: if the new snapshot id is already in the complete set the push refuses before writing anything, so the compensating delete can never remove another snapshot's valid manifest; the delete argv names only the manifest of the snapshot being pushed.
- PD-6 WHOLE-TREE CHECK EVERY PUSH: no sampling, no periodic variant, no skip when "nothing changed", no time limit, no change to `TimeoutStartSec` or `_RCLONE_TIMEOUT_S`. Measured cost goes to the SUMMARY and RUNBOOK with the "double, not real S3" label. Any operating policy is a new decision.
- PD-7 Paths containing a newline or carriage return are refused (the subset and listing mechanics are line based); other unsafe keys are already refused by `verify_bundle`.
- PD-8 Error texts are bounded: at most 5 paths are named, then "and N more"; every text goes through the existing scrubbing; fixed message heads are binding because tests and RUNBOOK cite them: "parquet push refused: path(s) already published with different content", "parquet push refused: remote object(s) differ from the local file(s) and no complete snapshot names them", "parquet verification failed", "manifest verification failed: snapshot {id} left incomplete", "manifest verification failed AND the manifest of snapshot {id} could not be removed", "unreadable manifest of complete snapshot {id}", "snapshot id {id} already exists on the remote".
- PD-9 After Task 4 passes, a small follow-up commit flips the docs from "real-S3 gate pending" to "passed"; if Task 4 fails nothing in the repo changes except the SUMMARY addendum and the user decides (D064: work stops at a checkpoint).

Failure windows of the design (stated honestly; copied into RUNBOOK 11):
- W1 the process is killed or the host is lost after the manifest object exists on the remote and before its check, or its removal, has finished: the snapshot looks complete with an unverified manifest. The window lasts about one single-object cryptcheck per push. Consequence: a restore verifies every pulled file against the pulled manifest and fails closed if it is wrong; the next push reads that manifest in the known set and a wrong hash becomes a hard failure, never a silent skip.
- W2 the compensating delete fails twice: the snapshot looks complete with a manifest that failed its check; the push exits non-zero and the message names the snapshot and the manual removal.
- W3 a crash between the Parquet upload and the manifest: orphan Parquet objects and an incomplete snapshot directory. Orphans are adopted after verification by the next push; pull and retention ignore the incomplete directory (retention purges it once a newer complete snapshot exists).
- W4 two writers at the same time (a second host) are not supported; the local backup lock only serialises one bundle root. Unchanged assumption.
- W5 cryptcheck proves the remote matches the local file at check time; an object changed after the check and before the next push is found at the next push.
