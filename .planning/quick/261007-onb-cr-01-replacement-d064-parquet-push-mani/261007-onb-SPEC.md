## Design to implement (D064)

Code under change: `src/ops/backup_remote.py` (`push_snapshot`, ~lines 308-339; helpers `check_sentinel`, `list_complete_snapshots`, `_call`, `_snapshot_filters`, `_crypt`), `src/ops/backup.py` (`verify_bundle`, manifest = flat mapping path -> sha256, `BackupBundle`, `prune_bundle`), tests `tests/test_backup_remote.py` (FakeRclone, StoreRclone, `_pushed_store`, the `test_a_changed_parquet_file_makes_the_immutable_copy_fail` family) and `tests/test_docker_backup_remote.py` (real rclone against an `rclone serve s3` double; the existing test at about line 234 already runs cryptcheck on `pg.dump`, and shows it fails when a local file changes LENGTH, but not when it changes with the same size). Use `codegraph explore "push_snapshot list_complete_snapshots verify_bundle prune_bundle"` before reading Python.

Decision of record: content identity is decided by SHA-256 against the manifest, never by rclone size, mtime, `--size-only` or `--checksum`. The manifest schema stays EXACTLY path -> sha256 (no mtime, created_at, size: `verify_bundle` requires a str-to-str mapping and `bundle_sha256` must stay reproducible, D-12). `--immutable` stays as defence in depth only.

Pre-upload decision for every local Parquet path (the bundle manifest paths under `parquet/`), against the KNOWN set of the complete remote snapshots (a snapshot is complete when its `manifest.json` exists, `list_complete_snapshots`):
1. path known with the same sha256 -> skip upload;
2. path known with a different sha256 -> hard failure, nothing uploaded over it, no overwrite, clear error naming the path;
3. path new to every complete manifest and absent from the remote -> upload;
4. path new to every complete manifest but already present on the remote (typical after a push that died between the Parquet copy and the manifest copy, because the existing order is Parquet, then pg.dump, then manifest last) -> verify that the remote content equals the local file (cryptcheck for that path) and adopt it (no upload) when identical, hard failure when different. A blanket "fail" here is WRONG: it would let one interrupted push block every later push.
Different size at the same path is case 2 or case 4 as applicable and is also a hard failure without overwrite.

Which manifests define the KNOWN set is a plan decision to propose (do not decide silently): the union of all complete remote manifests (small, readable with `rclone cat`) versus a remote listing (`lsf -R` of `parquet/`, decrypted names). Facts to weigh, verified: `prune_bundle` removes stale local files while the remote `parquet/` tree is never pruned (`apply_retention` never touches `parquet/`), so the newest manifest alone does not know paths pruned locally earlier; retention can purge old snapshots (and their manifests), so a union of surviving manifests can also forget a path that is still on the remote. The plan states the trade-offs and takes the fail-closed choice (an unknown remote path is never silently overwritten).

Post-upload verification: `rclone cryptcheck` over the whole Parquet tree and `pg.dump` BEFORE `manifest.json` is published; a cryptcheck failure leaves the snapshot incomplete and no new manifest is published (a snapshot without `manifest.json` is not complete and retention already ignores it). `manifest.json` itself can only be verified after upload, so the plan must add and prove a compensating step: if the post-upload check of the manifest fails, remove the just-uploaded manifest (or upload under a temporary name and rename; renames on S3 are copy plus delete, which needs its own real proof) so that the snapshot never looks complete. State the failure windows honestly (a crash between uploading the manifest and verifying it).
