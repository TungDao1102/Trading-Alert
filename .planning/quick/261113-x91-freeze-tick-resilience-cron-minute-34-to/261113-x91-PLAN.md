## Part 2: host tick, what would be compared, how a tick is tied to its slot, and why this plan stops

**What the reconciler trusts today (read from the code, not assumed).**

- `freeze_evidence_report` (`src/paper/coverage.py` 1021-1128) satisfies a slot only with a GitHub
  run from the exported run list. The run must have `event == "schedule"` and be assigned to
  `_latest_slot_not_after(run.created_at_utc, minute)`, with `run.created_at_utc - slot <= grace`
  (`_run_verdict`). Its line, matched by `run_id`, must pass `_line_verdict`: outcome `clean`,
  `event_name == "schedule"`, `schedule == cron` and `run_attempt == "1"`.
- The instant that decides lateness is GitHub's `created_at`. It is written by GitHub, not by the
  process that wrote the line, and anyone with read access can fetch it again from the GitHub API
  until the run expires. The line's own `checked_at_utc` never decides lateness.
- A line alone never satisfies a slot. Two tests pin this: `test_a_line_that_names_a_missing_run_cannot_satisfy_a_slot`
  ("The run list is the proof a scheduled run existed; a line alone is not enough") and
  `test_a_clean_line_without_run_metadata_cannot_satisfy_a_slot`.
- Every non-clean dated line after the pin ends continuity (`breaks`), whatever wrote it. The
  evaluator (`evaluate_trial`, `src/paper/exit_criteria.py` 1361) and the exporter (`_build`,
  `scripts/export_soak_evidence.py` 709) both call `freeze_evidence_report` on the merged log. The
  "single epoch" and "pinned hash unchanged" criteria already read every line after the pin
  (`epoch_id`, `pinned_hash`, `current_hash`).

**A host line, whatever option is chosen.** The host line is written by the same CLI
(`python -m src.paper.freeze --check --from-allowlist`), inside the recorded soak image
(`/app/params`, the registry the runtime actually reads). It runs against a scratch copy of the
pinned epoch file, never the runtime's own file, because `run_check_cli` rewrites the pinned-state
file on a REGISTRY_DIFF rollover. Fields that would be compared:

| Field | Rule |
|---|---|
| `outcome` | Only `clean` can satisfy. A SKIPPED, REGISTRY_DIFF or unreadable line never satisfies and ends continuity (existing `breaks`). |
| `epoch_id`, `pinned_hash`, `current_hash` | Must equal the pin (existing "single epoch" and "pinned hash unchanged" criteria). |
| `run_metadata.source` | `host`. GitHub lines keep today's metadata, and a line without `source` is a GitHub line. A host line carries no `run_id`, so it can never satisfy through the GitHub path. |
| `run_metadata.tick_id` | Unique. If one tick id appears on two different lines, neither counts, and the exporter refuses the merge (exit 4) as it does for a GitHub identity conflict. A replayed line restates its own instant, so it can only ever point at its own slot. |
| `run_metadata.schedule` | Must equal the evaluated cron (the unit is installed from the workflow cron); otherwise SCHEDULE_MISMATCH. |
| `run_metadata.commit` | The image GIT_SHA, for provenance only. |
| `checked_at_utc` | Stamped by the CLI from its injected clock (in production `datetime.now(UTC)`, read after the registry is read). |

Tying a tick to a slot: slot = `_latest_slot_not_after(instant, minute)`, the same rule as for
GitHub runs. A host tick serves exactly that one slot. It satisfies the slot only if
`instant - slot <= 1800 s`. A tick at or before the pin is auxiliary. The timer fires at the cron
minute with `Persistent=false` (no catch-up tick after downtime), and no time is passed in argv or
the environment. Grace, slot grid, minute list, thresholds and D065 item 4 do not change.

**The open question: which instant decides lateness, and who stamps it.**

- **Option `host-clock`.** The instant is `checked_at_utc`, stamped by the freeze CLI on the soak
  host. The software cannot backdate it: there is no time input, and a late firing is stamped late,
  so a late tick is still a gap. But anyone who can write the host log or set the host clock can
  write an on-time-looking line for a tick that ran late or never ran, and nobody can verify it
  afterwards. That makes "a line alone" enough for a host-satisfied slot, which is exactly what the
  reconciler was built to refuse. A hash chain (a sequence number plus the sha256 of the previous
  host line) only shows edits to lines older than a state that was already published. It cannot
  show a forged newest line or a wrong clock. This option weakens the evidence standard. It can be
  adopted only if the owner explicitly accepts, in the DECISIONS row, that host-satisfied slots rest
  on self-attested time.
- **Option `s3-witness` (recommended).** After the check, the host unit uploads the exact line bytes
  as a create-only object `<EVIDENCE_S3_PREFIX>/<epoch_id>/host-ticks/<tick_id>.jsonl` to the
  existing evidence remote (`EVIDENCES3`, `rclone rcat --immutable`, 16-DEC-O-01 option a,
  versioning on). The instant that decides lateness is the object's server-side LastModified,
  stamped by the S3 provider. The operator lists it with `rclone lsjson --use-server-modtime`. The
  rclone documentation (read 2026-11-13 through Context7) says that with this flag the modification
  time "becomes the time the object was uploaded". Without the flag rclone reports metadata written
  by the client, which must never be used. The listing goes to the exporter as a witness file and
  is copied byte for byte into the bundle, like `github_runs.json`. A host tick satisfies its slot
  only if slot <= `checked_at_utc` <= witnessed time, witnessed time minus slot <= 1800 s, and the
  object's sha256 equals the line's. It cannot be backdated. The provider stamps LastModified at
  upload, the create-only key and `--immutable` refuse changed bytes, a rewrite would be a new
  version with a later time, and deleting a version only removes evidence, which then shows as a
  gap. Cost:
  - one network call per tick. A failed upload means that host tick does not count; the GitHub
    tick may still cover the slot.
  - the evidence credential must reach a systemd unit on the host. Today RUNBOOK 20.7 and O-01 keep
    it in the export shell only, and "nothing on the host writes evidence by itself". Changing that
    is an amendment of O-01, which is the owner's call.
  - a new bundle input, an exporter flag, the loader, the evaluator wiring, the deploy unit and its
    tests. That is about two plans of work, not a third task of this plan.
- **Option `part-1-only`.** Ship the cron change. Part 2 is not built, or it is deferred.
- **Considered and not offered:**
  - the ping log of the heartbeat monitor as the witness. The monitor keeps a short ping history
    compared with a 14-day window, and reading it needs an API key off the host.
  - an RFC 3161 timestamp authority. It adds a new external trust root and a dependency.
  - a host-triggered `workflow_dispatch`. It needs a GitHub write token on the host, it changes the
    rule that non-schedule runs are not tick evidence, and it is not the same CLI on the host.
